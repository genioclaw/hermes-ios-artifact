Product summary

A native home for recurring work, with chat as the front door.

The app connects to one Hermes Agent gateway the owner runs. Briefings stay read-only. Anything consequential pauses for an explicit decision. The Knowledge Map shows what Hermes believes, where each belief came from, how confident it is, and who can see it, and lets the owner correct or remove it.

Contract boundary. Hermes Agent's API server documents chat, responses, runs with SSE events and approvals, sessions, and scheduled jobs. It does not document structured UI blocks, learning records, shopping offers, or a knowledge-graph API. Those surfaces need either a verified gateway capability or a client convention agreed in discovery. This page invents no endpoints. See PRD.md for the full mapping and the open questions.

Structured blocks

Typed, versioned content (lesson, flag, product, comparison, briefing, approval, graph). Every block carries plain-text fallback. Unknown types render as text and are never dropped.

Governed memory

Each node has provenance, confidence, privacy class, and correction state. Deletion is a tombstone the gateway must confirm, not just a hidden node.

Private by construction

Token in Keychain, Face ID gate, TLS over a private route, no vendor relay, no analytics, redacted notifications.

Block envelope (proposed client contract)

ContentBlock { type, version, id, fallbackText, provenance[],
               sensitivity, payload }
type ∈ lesson | flagQuiz | product | comparison | briefing
     | approval | graphPatch | citation
Unknown type or version → render fallbackText. Never discard.
